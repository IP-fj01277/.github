<h2>三步测完，不需要专业工具</h2>
<p>测住宅 IP 的速度，不必装一堆软件。一个在线测速页、一条命令、加一次实际登录，三步就能得到足够判断的数据。</p>
<p>关键是测对时段、测够样本、并且知道该看哪个数字。这篇把三步讲清楚。</p>

<h2>第一步：在线测速，看带宽</h2>
<p>用在线测速页跑三次：工作日上午、目标时区晚间、以及凌晨。三次的结果放在一起看，重点不是最高值，而是最低值。</p>
<p>最低值才是你在业务高峰时真正能用的带宽。只看最高值，等于自欺欺人。</p>

<h2>第二步：命令行测延迟与丢包</h2>
<p>对目标平台域名连续发起请求，一百次以上。看三个数：平均延迟、最大延迟、以及丢失比例。</p>
<p>平均延迟反映常态体验，最大延迟反映最差情况，丢失比例反映链路质量。三个数一起看，才能判断这条线路能不能承载日常操作。</p>

<h2>第三步：实际登录，看体感</h2>
<p>前两步是客观指标，第三步是主观体感。打开目标后台，从点击到页面完全加载，用手机秒表计时。</p>
<p>这个数字最贴近真实使用感受。有时候指标看着不错，但页面加载几十个资源，实际等待时间依然很长。</p>

<h2>三步之间的关系</h2>
<p>第一步看吞吐能力，第二步看链路质量，第三步看综合体验。三步都过，这条线路可用；任何一步明显异常，就该往下查。</p>
<p>三步的顺序也有讲究：先测带宽，因为带宽不足时延迟测试没有意义；再测延迟，因为延迟高时体感测试只会更差。</p>

<h2>为什么要在目标时区的晚间测</h2>
<p>因为住宅线路的瓶颈出现在那边的高峰时段。你在自己方便的时间测，往往正好避开了最差的时段，得到的是偏乐观的数据。</p>
<p>换算一下时区，把测试安排在目标地区晚上八点到十点。这个时段的数据才代表真实使用体验。</p>

<h2>样本要够</h2>
<p>测一次不算测。带宽至少三次、延迟至少一百个包、体感至少三次登录。样本太少，结论会被偶然因素带偏。</p>
<p>尤其是丢包，十个包的样本完全没有意义。一百个包以上，结论才有参考价值。</p>

<h2>数据怎么记录</h2>
<p>记四列：时间、测试项、数值、备注。备注写环境变化，比如换了客户端、改了设置。三周之后你会有一份自己的基线数据。</p>
<p>有基线之后，「今天有点慢」就能变成「今天延迟比基线高百分之四十」，沟通和排查都更有效率。</p>

<h2>测试时的三个干扰项</h2>
<p>第一，本机在跑更新或同步。第二，无线信号弱，隔了墙或距离远。第三，其他设备在占用带宽，比如有人在下大文件。</p>
<p>三项都会让测试结果偏低。测之前先排除，否则你测的是本地问题，不是资源问题。</p>

<p>测速要分时段：本地白天、目标地区晚高峰、业务实际使用时段。三个时段的结果可能差一倍以上。只看一次测速数字，容易得出错误结论。建议连续测三天，取晚高峰的下限作为决策依据。</p>
<h2>常见问题</h2>
<h3>需要专门的测速工具吗</h3>
<p>不需要。在线测速页加系统自带命令足够。专业工具适合深度排查，日常判断用不上。</p>
<h3>测出来很慢，是不是资源有问题</h3>
<p>先排除本地干扰，再换一条地址对比。两边都换过还是慢，才是资源问题。</p>
<h3>延迟多少算正常</h3>
<p>美国西海岸到国内一百五十到二百五十毫秒属于正常。低于一百毫秒要怀疑出口位置。</p>
<h3>要不要每次都全套测</h3>
<p>新资源全套测，日常只测延迟和体感。全套测试的价值在于建立基线。</p>
